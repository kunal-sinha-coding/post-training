# Experiment Notes

## Session

- Date: August 13, 2026.
- Goal: Improve held-out MBPP pass@1 for Qwen3.5-0.8B using 299 training problems and 75 held-out problems.

## Starting Point

The base model scored 22/75, or 29.3 percent pass@1. The project used MBPP as a small and inexpensive environment for iterating on post-training methods.

## Cycle 1: Make GRPO produce a usable learning signal

### Hypothesis

A binary full-pass reward was too sparse for the weak base model because groups in which every candidate failed gave GRPO no relative preference signal.

### Experiment

The reward was decomposed into format, syntax, interface, execution, and partial test-progress components. Group-level reward variance and component metrics were added to W&B and local logs.

### Metrics

- The first dense-reward run produced nonzero reward variance and gradients on all five steps.
- Four steps had mixed rewards in every group. The remaining step had mixed rewards in seven of eight groups.
- Held-out pass@1 moved from 21/75 to 19/75 in that short run.

### What Went Well

The dense reward eliminated the all-zero learning signal and made partial progress observable.

### What Went Badly

Five optimizer steps were not enough to improve held-out correctness, and a usable gradient did not guarantee a directionally useful update.

### Learning

Reward variance is necessary for GRPO but is not sufficient for generalization. The direction of the shaped reward must also align with full correctness.

### Next Hypothesis

Give dense-reward GRPO a longer training budget and retain the best intermediate checkpoint because performance may not improve monotonically.

## Cycle 2: Train dense-reward GRPO longer

### Hypothesis

The dense reward would improve MBPP if the policy received enough updates, and checkpoint selection would preserve gains lost by later updates.

### Experiment

GRPO trained for ten epochs with four generations per prompt, an effective batch size of 32, and checkpoint evaluation every 25 optimizer steps.

### Metrics

- An earlier GRPO result scored 22/75, or 29.3 percent pass@1.
- Checkpoint 150 scored 30/75, or 40 percent pass@1.
- The final training checkpoint scored 26/75, or 34.7 percent pass@1.

### What Went Well

The longer budget produced an 11 percentage point absolute improvement over 29.3 percent, and best-checkpoint restoration preserved it.

### What Went Badly

Checkpoint performance was nonmonotonic. Using the final weights would have discarded much of the gain.

### Learning

Held-out evaluation and checkpoint selection are core parts of the training method rather than optional reporting.

### Next Hypothesis

Warm-start GRPO with supervised fine-tuning so the model begins RL with basic coding competence.

## Cycle 3: Add response-only SFT before GRPO

### Hypothesis

SFT should quickly teach function signatures, valid Python, output format, and common solution patterns before GRPO explores execution outcomes.

### Experiment

An optional response-only SFT stage was added before GRPO. Prompt tokens were masked from the cross-entropy loss. W&B logged per-batch loss, cumulative average loss, and moving-average loss.

### Metrics

- A five-batch smoke run completed successfully.
- Its batch losses were 1.374, 1.006, 1.036, 1.371, and 0.9086.
- The final cumulative average loss was 1.139.

### What Went Well

The SFT implementation trained on verified MBPP reference solutions and passed the focused test suite.

### What Went Badly

The first SFT-only run failed before training because baseline evaluation expected `results_log_path`, which was missing from the debug configuration.

### Learning

An SFT-only execution path should skip unrelated baseline work, and stage-specific smoke tests need complete logging configuration.

### Next Hypothesis

Evaluate the model before SFT and after each full epoch to measure whether the warm start improves held-out pass@1.

## Cycle 4: Evaluate one full SFT epoch

### Hypothesis

One supervised pass through the 299 training examples would produce a large early competence gain.

### Experiment

The base model was evaluated on all 75 held-out problems, trained for one SFT epoch with approximately ten optimizer batches, and evaluated again. The final SFT evaluation was designed to become the GRPO starting measurement without duplicate evaluation.

### Metrics

- Initial pass@1 was 22/75, or 29.3 percent.
- Post-SFT pass@1 was 27/75, or 36 percent.
- Format errors fell from four to one.
- Final batch loss was 0.6242, and cumulative epoch loss was 0.8150.

### What Went Well

One epoch produced a 6.7 percentage point absolute gain, or approximately a 23 percent relative improvement.

### What Went Badly

The 75-example evaluation is coarse because one problem changes pass@1 by approximately 1.33 percentage points.

### Learning

SFT efficiently captured an easy initial gain from direct demonstrations.

### Next Hypothesis

Continue SFT until held-out performance saturates, then apply GRPO to the strongest supervised checkpoint.

## Cycle 5: Extend SFT toward saturation

### Hypothesis

More supervised epochs might continue the rapid first-epoch improvement before reaching a practical ceiling.

### Experiment

SFT was configured for 100 epochs with a held-out evaluation after every epoch.

### Metrics

- The run was manually stopped during the epoch 24 evaluation.
- Training loss continued to decrease.
- Held-out pass@1 declined after the initial improvement.

### What Went Well

Per-epoch evaluation made the onset of overfitting visible.

### What Went Badly

The 299-example training set was small enough for supervised optimization to specialize quickly. Continuing toward 100 epochs consumed compute while evaluation performance deteriorated.

### Learning

One SFT epoch was useful, but extended SFT overfit this dataset. A lower SFT training loss was not evidence of better generalization.

### Next Hypothesis

Use exactly one SFT epoch as a warm start and let GRPO optimize execution outcomes afterward.

## Cycle 6: Run one SFT epoch followed by GRPO

### Hypothesis

SFT would provide the easy competence gain, and GRPO would then improve beyond imitation by rewarding any correct program.

### Experiment

The model trained for one SFT epoch and then entered the existing dense-reward GRPO stage with four generations per prompt. The post-SFT evaluation was reused at the GRPO boundary.

### Metrics

- Post-SFT pass@1 was 27/75, or 36 percent.
- GRPO reached 31/75, or 41.3 percent, at checkpoints 175, 350, and 425.
- GRPO without SFT had previously reached 30/75, or 40 percent.
- The active SFT plus GRPO run later fluctuated below its peak. Checkpoint 775 scored 29/75, or 38.7 percent.

### What Went Well

GRPO improved the SFT model from 36 percent to a 41.3 percent best checkpoint.

### What Went Badly

The improvement over no-SFT GRPO was only one held-out problem. Continued training did not preserve the peak.

### Learning

SFT changed how quickly the model reached useful performance but did not clearly raise the final ceiling. The 40 percent and 41.3 percent results should be treated as effectively tied without repeated seeds.

### Next Hypothesis

Understand why cumulative training reward continued increasing while held-out pass@1 stagnated.

## Cycle 7: Diagnose reward and evaluation divergence

### Hypothesis

GRPO was increasingly optimizing partial progress on the 299 training problems rather than full correctness on unseen problems.

### Experiment

The latest W&B run, `autumn-wave-23` with run ID `qwv7wv0d`, was inspected for cumulative reward components, held-out evaluations, group variance, and full-pass behavior.

### Metrics

- `training/average_reward` rose from approximately 0.253 near step 21 to approximately 0.336 near step 645.
- `training/average_reward/test_progress` rose from approximately 0.090 to 0.139 and contributed the largest increase.
- Held-out pass@1 peaked at 41.3 percent and later remained mostly between 36 and 40 percent.
- At sampled trainer step 720, `reward/mean_group_std` was approximately 0.190.
- At that step, `reward/mixed_group_fraction` was 1.0 and `reward/flat_group_fraction` was 0.
- Across 30 sampled W&B points, mixed-group fraction was usually 0.875 or 1.0, while flat-group fraction was usually 0 or 0.125.

### What Went Well

Four generations usually produced healthy within-prompt reward differences, so GRPO retained comparative signal.

### What Went Badly

The cumulative reward average hid recent deterioration, partial test progress could rise without full passage, and training repeatedly reused the same 299 prompts and tests. GRPO also trained on sampled candidates while evaluation used one greedy completion.

### Learning

Insufficient exploration was not the clearest bottleneck. The evidence pointed more strongly to training-set specialization and reward misalignment with held-out full correctness.

### Next Hypothesis

Keep four generations and test a dynamic reward that begins with dense partial credit but gradually shifts most weight toward full passage.

## Cycle 8: Automate plateau stopping

### Hypothesis

Automatically stopping after five checkpoints without a new pass@1 maximum would prevent wasted compute and preserve the best checkpoint.

### Experiment

A plateau watcher and RunPod stop supervisor were prepared for the active training process. The supervisor verified the pod through the RunPod REST API before it could become armed.

### Metrics

- The active run exceeded five consecutive checkpoints without a new maximum.
- RunPod pod verification returned HTTP 403 twice.

### What Went Well

The supervisor failed closed and did not interrupt training without verified pod-control authorization.

### What Went Badly

The injected `RUNPOD_API_KEY` existed but could not control the current pod. The automatic stop schedule had to be disarmed.

### Learning

Durable stopping automation depends on verifying external control permissions before relying on it. Local plateau detection and remote pod control should remain separate gates.

### Next Hypothesis

Fix RunPod authorization or use a reliable local process-stop mechanism, then run the dynamic-reward experiment with early stopping and best-checkpoint restoration.

## Session

- Date: August 14, 2026.
- Topic: Expand MBPP training coverage with hidden synthetic tests.

## Starting Point

The official MBPP training split contained 374 tasks. Reusing the visible assertions risked specializing the reward to narrow inputs, so the next experiment added programmatically generated tests without adding new task families.

## Cycle 9: Generate hidden tests from existing tasks

### Hypothesis

Mutating existing test inputs and evaluating them with trusted reference solutions would broaden reward coverage without the cost or semantic drift of LLM-generated tasks.

### Experiment

A deterministic generator created up to 20 additional tests per training task. The training loader optionally appended these tests to execution-only test code while keeping them out of model prompts and leaving validation unchanged.

### Metrics

- The generator produced 6,762 hidden tests across 374 tasks.
- A total of 260 tasks reached the requested 20 tests.
- Nine tasks produced no safe variants.
- All 30 repository tests passed.

### What Went Well

The generated tests expanded input coverage while preserving the existing task-family distribution and official validation split.

### What Went Badly

Some tasks did not support 20 distinct safe mutations, and nine tasks produced no accepted variants.

### Learning

Reference-backed mutation can cheaply widen tests, but safe programmatic diversity is limited by the structure and domains of the original assertions.

### Next Hypothesis

Confirm that GRPO loads and executes the hidden tests during an actual optimizer step.

## Cycle 10: Validate synthetic tests in one GRPO step

### Hypothesis

An explicit training metric would demonstrate that hidden tests reached reward execution rather than only loading successfully.

### Experiment

A one-step debug run enabled synthetic tests. The first attempt used a per-device batch size of one with two generations. After user approval, the batch size was changed to two and the exact training command was retried.

### Metrics

- The first attempt stopped before training because the generation batch size was not divisible by `num_generations`.
- The retry completed one GRPO step.
- The successful run logged `reward/synthetic_tests/mean = 20`.

### What Went Well

The successful metric established that each sampled task used 20 hidden tests during reward execution.

### What Went Badly

The initial smoke configuration violated TRL's divisibility requirement.

### Learning

For grouped GRPO sampling, the generation batch size must remain compatible with the number of generations even in minimal smoke configurations.

### Next Hypothesis

Run a comparable error-analysis batch with synthetic tests enabled to determine which failure patterns change.

## Cycle 11: Recover the strongest GRPO-only baseline

### Hypothesis

Identifying the exact 40 percent run would provide a reproducible baseline for evaluating broader hidden-test coverage.

### Experiment

Local artifacts and W&B metadata were matched to the strongest GRPO-only evaluation.

### Metrics

- W&B run `wvx9f3bt` reached 0.400 evaluation pass rate.
- The run used commit `5f384a2`, 370 steps, learning rate `1e-6`, four generations, batch size one, gradient accumulation 32, and restored checkpoint 150.

### What Went Well

The baseline was tied to an exact run, checkpoint, commit, and optimization configuration.

### What Went Badly

The final checkpoint was weaker than checkpoint 150, so the result depended on best-checkpoint restoration.

### Learning

The 0.400 baseline is a checkpoint-selected result and should be compared using the same evaluation protocol.

### Next Hypothesis

Use the recovered YAML with synthetic tests enabled and classify every new evaluation failure against the established baseline.

## Session

- Date: 2026-08-14
- Topic: Constraint-safe synthetic tests and fixed-dense GRPO training.

## Starting Point

The first synthetic artifact executed but contained inputs outside many task contracts. The reward transition also remained enabled in a run intended to use fixed-dense GRPO.

## Cycle 12: Audit unsafe synthetic tests

### Hypothesis

Reference execution alone would reject invalid synthetic inputs.

### Experiment

The artifact was audited for cross-argument and task-domain constraints that reference execution did not enforce.

### Metrics

- The initial artifact contained 6,762 assertions across 374 records.
- Of 691 tests with a container-length parameter, 419 violated the required relationship.
- Eleven tasks contained 60 assertions encoding accidental `None` results.

### What Went Well

The audit identified invalid-input mechanisms before the replacement run.

### What Went Badly

Oracle success admitted malformed matrices, invalid indices, unsorted inputs, invalid dimensions, and accidental reference behavior.

### Learning

Reference consistency does not prove that an input satisfies the task contract.

### Next Hypothesis

Constraint inference and preflight validation can make the artifact safe for training.

## Cycle 13: Restore fixed-dense reward

### Hypothesis

Removing the transition entirely would prevent it from silently returning through configuration.

### Experiment

Commit `c53b195` removed transition fields and logic from training code and both YAML files. It added a fixed-dense regression test.

### Metrics

- Fixed reward reports `reward/pass_weight = 0` and `reward/dense_weight = 1`.
- All 30 repository tests passed.

### What Went Well

The transition was removed at configuration and implementation levels.

### What Went Badly

Run `ik0yc3pv` reached step 217 with the unwanted transition and was invalid for the requested experiment.

### Learning

Critical experiment invariants should be enforced in code and tests.

### Next Hypothesis

The corrected reward can be paired with a validated synthetic artifact.

## Cycle 14: Infer constraints and validate tests

### Hypothesis

Cross-argument, shape, ordering, index, positivity, and oracle constraints could reject malformed variants.

### Experiment

Commit `767b9ca` added constraint inference, constraint-aware generation, a standalone validator, and loader validation. The generator resumed and repaired only failing tasks instead of regenerating every task.

### Metrics

- Validation reported zero errors across 374 records and 1,870 assertions.
- The target changed from `M = 20` to `M = 5` because task 692 has only six novel valid inputs.
- Every record contains exactly five accepted assertions.

### What Went Well

The artifact passed structural, uniqueness, inferred-domain, cross-argument, deterministic-oracle, and coverage checks.

### What Went Badly

Twenty distinct valid variants were infeasible for at least one finite-domain task.

### Learning

The global `M` must respect the smallest novel input space. Resume and targeted repair avoid unnecessary regeneration.

### Next Hypothesis

Five validated hidden tests per task will broaden reward coverage without invalid-domain failures.

## Cycle 16: Align evaluation and training rewards

### Commit Name

Align evaluation and training rewards.

### Description

Evaluation now uses the same dense reward scorer as GRPO training. Binary pass rate remains separate, and W&B also receives the literal `evaluation/pass@1` metric. Focused tests cover partial reward without a full pass.

### Why

The previous evaluation average reward was binary and duplicated pass@1. Matching the training reward makes checkpoint comparisons meaningful while preserving the correctness metric.

### Context

The change follows the review of W&B run `sparkling-sunset-30`, where the metric mismatch made the apparent training and evaluation divergence difficult to interpret. The repository instructions now require this context for every commit.


## Cycle 17: Prioritize full-pass reward

### Commit Name

Prioritize full-pass reward and baseline evaluation.

### Description

The reward now uses rounded coefficients of format 0.025, syntax 0.05, interface 0.025, partial-test progress 0.4, and full pass 0.5. The separate execution reward was removed. Default training now recomputes the baseline evaluation and runs for ten epochs.

### Why

Full correctness is the primary target, while the remaining components only provide within-batch diversity. Recomputing the baseline makes every run comparable.

### Context

This is the approved experiment following the W&B analysis of sparkling-sunset-30. It uses the full validation set and will be monitored through iterative error analysis.


## Cycle 18: Select and stop by evaluation pass rate

### Commit Name

Select checkpoints by evaluation pass and stop after patience exhaustion.

### Description

Checkpoint ranking now accepts the W&B-facing `pass` name and maps it to the stored `pass_at_1` metric. The default configuration enables a patience of three checkpoint evaluations without a strictly higher pass. Such a run requests trainer termination while retaining the best checkpoint. Focused tests cover the stopping behavior.

### Why

Held-out pass is the target metric, while cumulative training reward can plateau without generalization. Patience stopping prevents continued training after three non-improving evaluations.

### Context

This change implements the requested checkpoint selection and early stopping policy for the current full-validation training experiment. Generated logs and results remain uncommitted.


## Cycle 19: Add evaluation diagnostics

### Commit Name

Log evaluation diagnostics for reward alignment and exploration.

### Description

Evaluation metrics now include reward-component means, successful-example counts, unique-completion rate, repeated-completion fraction, token entropy, and optional reference-policy KL. These metrics are passed through the existing W&B evaluation logger.

### Why

The additional measurements distinguish reward misalignment, evaluation noise, and exploration collapse instead of inferring causes from pass@1 alone.

### Context

Entropy and diversity are measured on generated evaluation completions. Reference KL is recorded when the evaluated model exposes a reference policy; otherwise it is omitted because evaluating a separate reference model would change the experiment cost and setup.
