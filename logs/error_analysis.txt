## 4. Observed error patterns

### Wrong numeric result: 224 cases

These programs execute but produce an incorrect number. The 102 affected tasks span different algorithms, so the category is not one shared arithmetic bug.

- Task 48, “set all odd bits,” returns `1` for inputs 10, 20, and 30. The code inspects the least significant bit on each shift and ORs the constant `1`; it never shifts the set bit back to its original bit position.
- Task 136 calculates an electricity bill as `0.15 * kwh`. For 75 units, it returns 11.25 where the reference test expects 246.25. The implementation omits the tiered rates and fixed surcharge.
- Task 601 increments one global counter for every compatible pair. It returns 6 for a test whose longest chain has length 3. Counting pairwise compatibility is not the same as finding the longest valid chain.
- Task 83 is a string-valued counterpart: it sums Unicode code points and calls `chr`, producing `Ħ` for `abc` instead of reducing alphabet positions modulo 26 to produce `f`.

These examples show errors in algorithm selection and task-specific constraints, including bit positions, piecewise billing, longest-chain optimization, and alphabet arithmetic.

### Wrong string result: 79 cases

The returned type is a string, but its content or required representation is wrong. There are several distinct causes.

- Task 930 returns `Matched!`, while the expected value is the exact string `Found a match!`.
- Task 114 returns the string representation `[((6, 5, 8), 3), ...]`; the expected representation flattens each original tuple and appends its frequency, such as `(6, 5, 8, 3)`.
- Task 83 applies `chr` to the raw sum of Unicode code points. Its outputs are valid Unicode characters but do not follow the specified alphabet wraparound.

The tests make these exact string contracts observable. The common output type does not imply a common implementation fix.

### Wrong sequence length: 53 cases

The generated list or tuple has a different number of elements than expected.

- Task 13 calls `Counter.most_common()` without a limit and returns every word. The tests require only the top four. One actual result has seven entries where four are expected.
- Task 15 collects lowercase characters individually. For `AbCd`, it returns `['b', 'd']`; the required output is the substrings `['bC', 'd']`.
- Task 956 splits at uppercase letters in a way that consumes the separator characters. It returns an empty first segment and loses the uppercase initials.

These include missing limits, incorrect segmentation, and lost delimiter characters.

### Wrong sequence contents or shape: 38 cases

The returned collection is the wrong structure or contains incorrect elements. Task 951 returns index pairs such as `[(2, 0)]`, while the expected output is a list of tuple values. This is a contract interpretation error: the implementation computes where matches occur instead of returning the matching tuples requested by the tests.

### Wrong boolean result: 23 cases

The code returns a Boolean, but its predicate implements a different condition from the test contract.

- Task 26 checks whether each tuple's length equals `k`. The tests and reference behavior check whether all tuple elements equal `k`; for the first input, the implementation returns `False` instead of `True`.
- Task 179 defines a Keith number as a number equal to the sum of its digits. A Keith number requires a digit-sequence recurrence, so the implementation returns `False` for 14 and 197 even though both tests expect `True`.
- Task 899 checks a condition involving the minimum array element, rather than whether repeated removal from the array's two ends can produce a sorted order. All three tests expect `True`; its implementation returns `False` for all.

The code often resembles the task vocabulary while implementing the wrong predicate.

### `IndexError`: 23 cases

Ten programs index outside a sequence. Task 81 loops over the six elements of the first tuple and accesses the second tuple at the same index, although the second tuple has only three elements. The expected behavior repeats the shorter tuple using a modulo index. Task 324 similarly assumes each input element has a partner and crashes on an odd-length input. The tracebacks and candidate source lines are preserved for every case.

### Wrong sequence order: 18 cases

Seven programs return the right multiset in the wrong order. Task 915 rearranges positive and negative numbers but does not follow the expected ordering of the positive partition. Other cases include sorting by the wrong tuple component. The diagnostic file preserves actual and expected sequences so these can be separated from omissions and extra values.

### `TypeError`: 7 cases

Three programs apply operations to incompatible types.

- Task 202 applies `% 2` to a character rather than to its index. The task is about removing characters at even positions.
- Task 642 inserts list rows into a set. Lists are unhashable; the candidate must convert each row to a tuple or use another equality-based deduplication strategy.
- Task 910 compares month and day strings with integers instead of converting or validating the strings first.

### `NameError`: 6 cases

Two programs refer to undefined names. Task 198 uses `c` in Heron's formula although it never defines `c`; the whole formula also does not encode the stated ellipse problem. Task 205 uses `y` in a sort key lambda whose argument is named `x`, so `y` is out of scope.

### Other value mismatch: 6 cases

These residual mismatches do not share a useful single mechanism. They include a zero-based index where the tests expect a one-based position or `None`, a numeric result where the tests require the string `Not Possible`, and inaccurate geometry outputs. Their exact prompts, assertions, actual values, and expected values are retained in the JSON artifact.

### `ValueError`: 6 cases

Two programs make invalid lookup or conversion assumptions.

- Task 936 looks up each tuple's second value in the supplied ordering list, although the ordering contains tuple keys from the first position. This raises `ValueError` on every test.
- Task 949 converts characters from `str(tuple)` to integers. It encounters the opening parenthesis and raises `ValueError` instead of summing the digit lengths of the tuple elements.

### Malformed Python syntax: 3 cases

One task, ID 27, fails all three tests with an unterminated triple-quoted string. The completion repeats its docstring many times and ends before closing the final string. This is a generation truncation or repetition failure, not a problem in the test harness.

### `re.error`: 3 cases

Task 73 joins the delimiters with `r'|'` but does not escape the literal `*`. The resulting regular expression contains an operator with nothing to repeat and raises `re.error` on all three tests.

### Wrong set result: 3 cases

Task 490 detects symmetric pairs but leaves one pair in the orientation `(9, 8)` where the expected set contains `(8, 9)`. It recognizes the relationship but fails to canonicalize the output pair.

### Wrong mapping result: 3 cases

Task 561 creates keys only from each pair's first item. The expected mapping also contains keys for values that appear only as second items, with empty lists for those values. The candidate's construction rule omits those entries.

### Missing or `None` return: 3 cases

Task 907 prints lucky numbers one at a time and has no return statement. The reference and assertions expect a list. The task wording says “print,” but the callable contract in the tests requires returning the values.

## 5. Success patterns and controls

The 372 programs labeled `passed` each passed all three assertions. There were 107 partial programs: 49 passed one of three assertions, and 58 passed two. The other 113 non-syntax programs passed none; one additional program had malformed syntax. The replay exactly reproduced every saved `passed_tests` count, which is a strong check that the saved programs and test code were paired correctly.

The saved interface checker marked 590 of 593 candidates valid. Three were marked invalid, but two of those still passed the tests. Interface mismatch is therefore not the dominant explanation for the 221 programs with at least one replay failure. No replay timed out, and no sandbox or infrastructure error occurred.

## 6. Deep triage

Each failed test case has exactly one primary pattern in the JSON artifact. A task can have multiple patterns across its three test cases.

### Numeric and Boolean outputs

Observed evidence is a direct actual-versus-expected mismatch, not an exception. The candidate code for tasks 48, 136, 601, 26, 179, and 899 shows that the implementation uses an incomplete or incorrect task model. The strongest supported cause is specification or algorithm misunderstanding. An alternative for some cases is that three MBPP tests do not expose every distinction needed to infer behavior; these particular failures are nevertheless visible on the saved tests. Targeted tests with boundary values and counterexamples would distinguish a fragile formula from a broader misunderstanding.

### String and sequence outputs

The errors include lost characters, wrong output limits, incorrect nesting, missed items, and wrong order. Examples 13, 15, 114, 915, and 956 directly expose these mechanisms. Because this group is heterogeneous, adding generic string or list tasks alone is unlikely to fix every case. Data additions should state the required ordering, cardinality, output type, and delimiter behavior explicitly, then test those constraints with varied inputs.

### Runtime exceptions

Tracebacks identify concrete code sites. Indexing failures often reflect an assumption about sequence lengths or even-sized inputs. `NameError` identifies undeclared values. `TypeError` reflects using arithmetic or sets with the wrong value types. `ValueError` reflects a mismatched lookup key or parsing a representation rather than using the structured values. The regex failure is specifically an unescaped metacharacter. These causes are supported by task text, traceback, and source. A competing explanation for some errors is that model-written docstrings or comments distracted from the operative contract; this is not necessary to explain the captured failures.

### Syntax and missing returns

Task 27's code contains repeated docstrings and an unterminated triple quote. Task 907 completes its loop but prints instead of returning. These are separate failure mechanisms: malformed generation versus an output-contract mismatch. They should not be grouped with algorithm errors.

### Other, set, and mapping mismatches

The set and mapping examples have precise representation defects, but each appears in only one task. The six residual value mismatches are diverse. More data is needed before treating any of these as recurring root causes beyond their individual examples.

## 7. Shared causes and interactions

Most failures occur after valid Python executes: 450 of the 498 nonpassing test cases are assertion mismatches. This makes parser, function-interface, and environment failures poor explanations for the bulk of the checkpoint's errors. Numeric, string, sequence, and Boolean failures all indicate that the generated program often maps the task to a plausible but incorrect rule. Runtime exceptions are a smaller separate group, led by out-of-range indexing.

The reward can still distinguish partial progress. Of the 107 partial programs, 58 pass two of three tests and 49 pass one. A program that solves a common case but misses edge behavior receives partial test reward. That is useful signal, but it can leave a persistent ceiling when the policy learns only the easiest subset of each contract. This is a plausible interaction between sparse task coverage and partial reward, not a causal conclusion from this snapshot.

## 8. Underlying root-cause synthesis

The smallest credible synthesis has two parts.

1. **Task semantics are frequently implemented incorrectly.** This explains the 450 value mismatches. The code examples show multiple separate mechanisms: wrong formula, wrong recurrence, wrong selection limit, wrong sequence indexing, wrong return contract, and wrong text transformation. These are observed program defects. They do not point to one common code bug.
2. **A smaller set of generated programs has local robustness or completion failures.** The 45 runtime exceptions and one malformed program affect 14 distinct tasks when grouped by task ID, with overlapping patterns possible. Most are concrete indexing, type, name, conversion, and regex mistakes.

The growing training/evaluation gap supports further analysis of task diversity. The saved training greedy pass@1 rose from 32.55% at step 0 to 62.73% at step 830 and 70.32% at step 1300. Sampled W&B EvalPlus greedy pass@1 peaked at 54.0% at step 630, was 53.2% at step 830, and was 52.1% at step 1300. This run therefore shows continued training-pool gains after EvalPlus has stopped improving. It is consistent with over-specialization, but this error replay alone cannot show that task diversity would cause an evaluation gain.

The 11 same-wrong-output programs are a useful secondary signal for weak or degenerate solutions. They include constant answers and a print-only function. They account for 33 failing cases, but they are not all intentional hardcoding. The set and mapping errors, and the six heterogeneous output mismatches, remain residuals outside the two broad mechanisms above.

## 9. Proposed solutions and confirmation tests

1. **Build a targeted task-variant set from the observed error families.** Start with a small, balanced addition covering arithmetic and number theory, sequence and tuple transformations, and string or regex behavior. Use explicit input constraints, output types, ordering rules, and edge cases. Validate every generated reference and assertion with the sandbox, remove duplicates, and retain task provenance. This addresses the 224 numeric, 109 sequence, and 79 string mismatches. A confirmation run should compare greedy training and EvalPlus pass@1 against the same checkpoint protocol, and should check the added tasks separately for pass@1 and partial pass rate.
2. **Prioritize tasks with recurrent failures over tasks with one isolated miss.** The complete case file identifies all 221 failed task programs and their exact assertions. Re-sample task families with the highest failure counts, but cap each family so the new data does not simply over-weight arithmetic or list manipulation. A useful test is to train with one added family at a time and compare its targeted task variants, the unchanged 593-task training pool, and EvalPlus at the same checkpoint intervals.
3. **Add focused contrast examples for partial solutions.** For the 58 tasks that passed two of three tests, derive one or two tests that vary the argument responsible for the failed assertion, while preserving the original task contract. This tests whether more informative reward cases help the policy learn the missing behavior. Confirm with the same task-level case counts and evaluation set.
4. **Keep the rare defects as explicit validation checks.** Add regression examples for unequal sequence lengths, odd-length pairing, special regex characters, string-valued numeric inputs, and print-versus-return behavior. This should reduce the corresponding runtime and contract errors; confirm by rerunning the frozen checkpoint and any new checkpoint on the exact saved assertions.

No training data or model changes were applied during this report. The proposed changes require a separate controlled experiment.

## 10. Limitations

- The checkpoint archive contains one greedy generation per training task, not every rollout sampled during training. The full 168,960-row reward trace is separate and covers many training steps. This report intentionally analyzes only checkpoint 830's 593 saved training-set greedy programs.
- Each task has three original MBPP assertions. Errors on these cases do not establish performance on all possible inputs.
- The failure taxonomy is mechanical and mutually exclusive per failed test case. For assertion mismatches, it uses the type and shape of actual and expected values. It does not infer a unique algorithmic cause for every numeric or string mismatch. The full prompt, reference solution, assertion, generated code archive, traceback, and comparison values are retained to make follow-up review possible.
- The test code used for diagnosis was recovered from the reward trace and matched by task ID. There were no unmatched or conflicting IDs.
- The repository describes its subprocess harness as intended for local experiments, not hostile-code isolation. A static AST screen found no filesystem, network, shell, subprocess, or dynamic-evaluation calls among these completions, but this is not a formal security guarantee.
- W&B curve retrieval was sampled. Reward diagnostics used 50 points across internal steps 13,074 to 250,199 of 262,085. The evaluation query returned a 100-row sample across internal steps 0 to 260,697. Exact target-step retrieval was unavailable through the MCP. Local checkpoint metrics are exact.
- This analysis did not run a new training experiment or establish that any proposed data change improves EvalPlus.

5. Success patterns and controls

All 232 latest MBPP successes passed the same evaluator and input protocol, so there is no universal inability to load or execute the model. Of the 146 failures, 145 parse as Python and one is invalid syntax. The visible assertion replay passes only 20 failures and rejects 126. For the persistent subset it rejects 93 of 107. The visible rejections comprise 101 assertion mismatches, 23 other runtime errors, one syntax error, and one timeout. They demonstrate that many failures are detectable with information already in the prompt. They do not show that repair will succeed.

There are 143 saved failing-input records. Replays restore tuple and complex argument types from canonical base inputs before calling each function. All 143 references return normally. Candidate calls yield 118 different representations, 24 exceptions, and one timeout. No saved failing arguments exist for tasks 126, 129, and 233; their visible-assertion failures are still retained. Direct reference comparison is diagnostic only and does not replace special EvalPlus oracle rules.

6. Deep triage

Wrong algorithm or formula:
Observed evidence: Evidence includes XOR != 0 for exactly one differing bit, Fibonacci recurrence for Bell numbers, and a pentagonal formula for a nonagonal number. Most programs are fluent, short, and executable but encode the wrong invariant or formula.
Likely causes and alternatives: The leading explanation is missing or poorly ranked algorithmic knowledge that generic test-reward updates do not reliably correct on unseen tasks. A plausible alternative is that the correct program remains in the model distribution but is not greedy. Existing samples support that alternative for part of the failure set.
Targeted intervention and confirmation: Use verified teacher solutions on independently sourced training problems for the same algorithm families, then test single-generation accuracy on a development split and an untouched benchmark. For inference, use visible-example rejection plus repair. Do not train directly on these benchmark solutions.

Wrong interpretation of the task:
Observed evidence: The code performs a different requested operation, such as adjacent tuple-coordinate gaps instead of within-tuple differences or a sum of squares instead of a difference.
Likely causes and alternatives: The leading explanation is weak specification-to-operation grounding, rather than a Python parser defect. Terse prompts and ambiguous language can contribute, but explicit examples often already contradict the code.
Targeted intervention and confirmation: Train on contrastive task pairs that differ in one requirement, with verified implementations and output contracts. A prompt-paraphrase ablation can test prompt sensitivity without changing the reference task.

Runtime, API, or termination error:
Observed evidence: The code contains tuple/list concatenation, wrong entry-point names, out-of-range indexing, undefined variables, illegal conversions, and a nonadvancing loop. These defects were checked against actual source and replay results.
Likely causes and alternatives: The leading explanation is insufficient execution-aware checking. API conventions and function-name copying contribute. A global environment problem is unlikely because the same sandbox executes the reference implementations and most benchmark tasks pass.
Targeted intervention and confirmation: At inference, compile, validate the named entry point and call signature, execute only the provided example, and feed a bounded error message into a repair attempt. Measure selected-solution accuracy at a declared inference budget separately from raw greedy pass@1.

Wrong output type, shape, or order:
Observed evidence: Core work can be close, but the output is nested rather than flattened, strings rather than integers, or sorted in the wrong direction.
Likely causes and alternatives: The leading explanation is weak type, shape, and ordering contract enforcement. It can overlap with specification errors; the primary label identifies the most local observable defect.
Targeted intervention and confirmation: Use training tests that distinguish output type, shape, ordering, and boundary cases, with paired corrected examples. A visible-test repair should remove directly exposed contract failures when a correct repair is available.

Boundary or character-case handling:
Observed evidence: Programs mishandle positive-only rotation, inclusive bounds, case conversion, uppercase prefixes, or equality at a threshold.
Likely causes and alternatives: The leading explanation is overgeneralization from a narrow pattern or one example. Some cases fail the displayed example, so they are not all obscure hidden-test failures.
Targeted intervention and confirmation: Add boundary-focused independent training problems and tests around zero, equality, terminal indices, and letter case. Compare gains on unseen boundary cases rather than training reward alone.

Ambiguous or conflicting benchmark contract:
Observed evidence: Four cases have conflicts or missing conventions: tuple member equivalence, polar versus rectangular conversion, row versus column averaging, and a missing-second-value sentinel. The visible assertion disambiguates several even where prose is poor.
Likely causes and alternatives: Benchmark-contract ambiguity is real but small. It cannot explain 142 other failures. A separate task 430 also has a questionable reference formula, but its generated formula is independently wrong and remains classified as an algorithm error.
Targeted intervention and confirmation: Report canonical scores unchanged, maintain a separately flagged ambiguity slice, and test prompt clarification only as a distinct diagnostic. Do not silently edit official tests or subtract these tasks from the headline score.

Invalid Python syntax:
Observed evidence: Task 129 assigns row_sums = sum(row) for row in matrix without the required comprehension brackets or generator parentheses. This is invalid Python.
Likely causes and alternatives: There is only one syntax failure. This does not support a universal format, stopping, or truncation explanation for the plateau. The classification is syntax, with no claim that the generation was truncated.
Targeted intervention and confirmation: Use a compile check followed by one repair attempt. Keep the original greedy score separate from repaired accuracy.

7. Shared causes and interactions

All four main runs share the 0.5B base model, rank-16 LoRA adaptation, test-based GRPO supervision, and the greedy evaluation protocol. Changing the task pool does not separately test model size, learning objective, teacher knowledge transfer, or inference-time checking. Equal aggregate scores are therefore evidence of a shared bottleneck in this setup, not proof of a universal model-size limit.

The current saved trace contains 9632 complete task groups of 16. Exact category counts are: 4658 groups with both full successes and failures, 1549 varying groups with no full success, 2746 all-correct groups, 298 all-zero groups, and 381 equal partial-reward groups. No group contains mixed task IDs. Thus 64.44 percent vary, but only 48.36 percent contrast a correct solution with an incorrect solution. Among the final 1632 recorded groups, 889 vary (54.47 percent), including 659 correct-versus-incorrect groups (40.38 percent). Variation declines but has not disappeared. Of 61,389 candidates strictly above their own group mean, 14,262 (23.23 percent) remain incomplete. These are candidate counts, not measured gradient contribution.

Batch reward scaling changes the denominator, but TRL 0.25.0 still subtracts the per-task group mean. All-equal task groups therefore have zero reward-derived relative advantage even when other tasks in the batch vary. KL can still contribute. This is confirmed in the installed grpo_trainer.py lines 1600 to 1620 and the official versioned documentation: https://huggingface.co/docs/trl/v0.25.0/grpo_trainer. The local log frac_reward_zero_std should not substitute for the custom within-task metric when scale_rewards is batch.

The training pool has 591 original tasks and 8879 OpenCode tasks. Uniform sampling allocates 6.24 percent of task draws to originals. Saved rollout coverage contains 597 original groups from 590 unique original IDs, and 9035 OpenCode groups from 8852 unique OpenCode IDs. This is about one pass over the original pool. Original-only training at a similar optimizer-step count has far more original-task exposure. Therefore the four mixtures are not matched ablations of original-domain exposure. In the earlier hard-synthetic setup, about 90 percent of task draws were synthetic, and the prior audit found many partial-only comparisons.

8. Underlying root-cause synthesis

A. Semantic and knowledge-transfer limits explain the largest observed error slice: 68 algorithm errors, 33 interpretation errors, and 5 local boundary errors, totaling 106/146 or 72.60 percent. In the persistent subset these categories total 82/107 or 76.64 percent. The causal hypothesis is that shared base-model priors and test-based on-policy updates improve common training behaviors without supplying enough correct solutions or contrastive specifications for these unseen patterns. The matching task failures and repeated formula confusions support this hypothesis. Correct sampled candidates are a competing explanation for some tasks, so this is not proof of absent knowledge. The discriminator is independently verified teacher-solution SFT versus compute-matched additional GRPO.

B. Lack of execution-aware selection explains a separate practical weakness. Runtime and output-contract categories total 35/146 or 23.97 percent. More broadly, 126/146 fail the prompt-visible assertion. These sets overlap, so the 126 must not be added to the primary category counts. Correct programs are sometimes sampled but not greedy, and simple rejection can identify many current wrong programs. The discriminator is a fixed candidate budget with selection based only on the supplied assertion and observable execution, followed by hidden-test scoring after selection. Passing the visible example alone will not resolve the remaining semantic and edge failures.

C. Training-signal allocation is a plausible upstream contributor, not an assigned per-example cause. Thirty-five point five six percent of saved groups have equal rewards and 16.08 percent vary without a full success. OpenCode dominates the data draws. This combination can improve the training objective without adding enough signal for the persistent MBPP slice. The discriminator is a compute-matched curriculum or mixture-weight ablation with original exposure recorded, while preserving independent evaluation. The current audit does not establish that changing normalization alone will help.

D. Residual benchmark conventions explain four primary cases, or 2.74 percent, and invalid syntax explains one, or 0.68 percent. These residuals are too small to account for the shared plateau. Model capacity remains a possible contributor to semantic failures, but existing sampled successes rule out a hard 60-percent solvability ceiling. Absence of success in the finite sample is not evidence of impossibility.

Existing original-only checkpoint samples quantify this distinction. Checkpoint 630 has 304/378 MBPP tasks with at least one successful candidate among 16 (80.42 percent), and checkpoint 830 has 291/378 (76.98 percent). Of the 107 common greedy failures, 37 are recovered in the 630 sample and 26 in the 830 sample, with 42 distinct tasks recovered across both sets. Twenty-seven have a full base-plus-extra success across those sets. These are oracle availability measurements, not deployment scores. The historical checkpoints were selected using benchmark performance.

9. Proposed solutions and confirmation tests

Priority 1, immediate inference mitigation: add a separate evaluation harness for generation, compile/API validation, execution of the assertion supplied in the prompt, and a bounded repair attempt from that observable error. Use no hidden expected outputs during selection or repair. Predeclare the candidate and token budget and report selected-solution accuracy and cost separately from greedy pass@1. Start on an independent development batch. The predicted benefit is removal of directly exposed runtime, contract, and algorithm failures when a valid correction is generated. The risk is overfitting the visible example, which must be checked with hidden tests only after candidate selection. No such fix was implemented here.

Priority 2, improve true single-generation behavior: teacher-solution SFT on independently sourced, verified training tasks for observed weak algorithm, specification, and contract families, then compare SFT alone, GRPO alone, and SFT followed by GRPO with matched budgets. Include contract-preserving function names, exact types and ordering, and multiple independent tests. Evaluate raw greedy MBPP and MBPP+ separately. Do not use the benchmark task solutions as training demonstrations. This aims to supply corrections rather than only relative scores on existing candidates. Successful sampled solutions can supply rejection-sampling SFT data on training tasks. Teacher quality and in-domain memorization remain risks. STaR is a related demonstration-bootstrapping method, not evidence that it will solve this coding setup: https://arxiv.org/abs/2203.14465.

Priority 3, improve training signal: compare the current uniform mix against an explicit original-domain sampling weight and a training-only curriculum favoring tasks with some full successes and some failures. Record both optimizer compute and original-task draws so gains cannot be explained by exposure alone. Consider a full-pass-focused reward ablation, but retain a comparison to partial shaping because discarding partial-only tasks can remove hard learning opportunities. Measure held-out task-type transfer and counts of correct-versus-incorrect groups, not mixed fraction alone.

Priority 4, test capacity and adapter limits with controlled comparisons: use the same verified data, prompt, compute accounting, and decoding protocol for a larger base model or a separate adapter-capacity ablation. A substantial persistent-slice improvement under these controls would support a capacity or adaptation hypothesis. A similar plateau would shift attention to supervision and evaluation design. The current data-mix experiments cannot separate these causes.

An untouched benchmark or fresh held-out set is needed for a new generalization claim because repeated inspection makes this MBPP set a development resource. The 107 failures may guide a taxonomy, but should not become a memorized training set.

10. Limitations

All counts are retrospective observations from one latest snapshot per mix. Latest steps differ (660 to 1340), and rollout implementations and reward scaling differ. The comparison is not randomized or compute matched. Primary causes are manual interpretations of current code, with per-task evidence and confidence preserved. The same task may have a different error in another run. One greedy output cannot establish the model distribution, and the older 16-sample checkpoints are not the current OpenCode checkpoint. Oracle unions and any-of-16 use hidden labels only for post-selection measurement. Direct reference repr checks are not full special-oracle rescoring. Training sample metrics are in-sample. Saved trace coverage is 9632 groups, while optimizer logs contain 1207 steps, so three batches worth of candidate trace rows are absent relative to 1207 times eight and no exact step mapping is asserted. No new training, generation, model repair, or official test changes were performed.

6. Deep triage

### Jev overcalls tools
Observed evidence is the confusion distribution and representative unrelated-tool questions. A likely cause is that the model gives high weight to any available tool and insufficient weight to whether its domain matches the user request. An alternative is benchmark-specific label semantics that differ from ordinary assistant behavior. A targeted test is to add an explicit compatibility instruction and evaluate it on a train-derived held-out set. The prompt sweep's definitions and strict variants did not help, so wording alone is unlikely to solve this pattern.

### Impossible versus missing information
Observed evidence is the 336 and 234 directional confusions. The likely cause is ambiguity in whether a partially relevant tool is considered sufficient. A competing cause is duplicate or near-duplicate benchmark construction. A targeted test is nearest-neighbor retrieval from training questions and a tool-schema compatibility score, evaluated without target metadata.

### Frozen Jina weakness
Observed evidence is that pretrained and fine-tuned frozen features both remain below the end-to-end checkpoint. The likely cause is that mean pooling loses the fine distinctions between tool availability and missing arguments. A competing cause is noisy heuristic training labels. A targeted test is end-to-end pairwise training with more preference pairs and a held-out training slice.

### Ranker tool-call bias
Observed evidence is that 1,977 non-tool rows become tool_call. The likely cause is an imbalanced or too-easy binary preference objective: chosen responses are often tool calls, while candidate ranking needs calibrated four-way discrimination. A competing cause is truncation of long contexts or response candidates. A targeted test is class-balanced four-way candidate training, response-type-balanced sampling, and per-class calibration on a held-out preference split.

7. Shared causes and interactions
The Jev and ranker failures share a tool availability decision. The ranker shows a stronger version because its preference labels reward chosen responses without directly training the four-way class boundary. Jina's question-only setup cannot inspect the answer choices, while the ranker can inspect them but needs better negative and class-balanced supervision.

8. Underlying root-cause synthesis
The main upstream mechanism is incomplete modeling of tool compatibility. It explains Jev's tool overcalls and the ranker's tool-call bias. A second mechanism is noisy or incomplete inferred labels in training, which affects all local supervised models. The residual Jev errors on near-duplicate cases may be irreducible without reproducing the benchmark's hidden generation policy.

9. Proposed solutions and confirmation tests
1. Train the ranker on all preference pairs with balanced batches and an explicit four-way response-class auxiliary loss. Confirm with the same full test denominator and require lower non-tool-to-tool errors.
2. Add a candidate validity feature for whether a tool-call response names an available tool, while keeping selection independent of target metadata. Confirm on a held-out train split before test evaluation.
3. Add nearest-neighbor retrieval from training questions and tool schemas as a second local scorer. Confirm whether it reduces Jev's cannot-answer versus request_for_info errors.
4. Preserve Jev as the current best inference baseline and test only targeted overrides on disagreement slices. Do not spend more API budget on unvalidated repeated voting.

The benchmark's remaining uncertainty is argument sufficiency after tool identity has been established.

9. Proposed solutions and confirmation tests
Keep strict argument evidence. Future improvements should use a train-derived normalization layer for dates, numbers, and common parameter synonyms, then validate against the same full route.

10. Limitations
This remains an exploratory repeated-test result. The lexical rule may not generalize to unseen tool schemas.

Iteration 20 explicit action language ablation

The candidate was a generic question-only action rule. When a valid candidate tool call remained classified as request_for_info, the rule switched it to tool_call when the question contained a whole-word action verb such as book, find, reserve, search, send, or delete. The rule used no labels or hidden test fields during prediction.

The strict argument-evidence route without this rule remained at accuracy 0.8981, macro precision 0.9086, macro recall 0.8874, and macro F1 0.8922. Adding the generic action rule reduced accuracy to 0.7965 and macro F1 to 0.7513. The rule overfires on cannot_answer examples whose questions contain ordinary action verbs. Reject this candidate and keep it configurable for reproducibility only.

The next hypothesis remains targeted value normalization. Dates, city aliases, implicit values, and schema defaults need narrow handling because broad action language is not a reliable intent signal.

Iteration 21 narrow value normalization

The candidate added a narrow evidence check for required argument values. It retained exact token matching, and added only ISO date values matched to month-name plus day plus year text, plus aliases SD for San Diego, LA or LAX for Los Angeles, and NYC for New York. It used no labels or hidden test fields during prediction.

The prior strict route scored accuracy 0.8981, macro precision 0.9086, macro recall 0.8874, and macro F1 0.8922. The normalized route scored accuracy 0.8987, macro precision 0.9094, macro recall 0.8879, and macro F1 0.8927. This is a small improvement. Keep the rule, but treat the gain as provisional because the alias list is narrow and benchmark-specific.

The updated error pattern remains concentrated in Live Simple. Further work should prefer schema-grounded normalization learned from training data rather than expanding aliases from test examples.

Iteration 22 route-label ablation

The normalized route was tested with narrower Jev routing sets. Routing request_for_info and tool_call but excluding direct reduced accuracy to 0.6684 and macro F1 to 0.7358. Routing request_for_info and direct but excluding tool_call scored accuracy 0.8916 and macro F1 0.8838. The full request_for_info, tool_call, and direct route remains best at accuracy 0.8987 and macro F1 0.8927. Keep the full route.
